# Declarative MDP terms alongside custom-JS terms

mjswan supports custom MDP terms (observations, terminations, events, commands, actions) by letting authors supply arbitrary TypeScript via `ObsFunc(ts_src=...)` / `register_obs_func`; at build time `_build_client.py` inlines that source into the engine bundle (see [ADR 0001](0001-npm-self-reference-for-custom-mdp-imports.md)). This is maximally flexible but means a built simulation can carry arbitrary author code. A downstream consumer that renders *untrusted* simulations with a single shared engine — notably mjswan Cloud, which loads one platform-pinned engine from a CDN and feeds it per-simulation data — cannot safely execute that code: it would run with the platform's origin authority.

Investigation of the built-in and example custom terms showed that ~98% are **bounded linear algebra over named physics quantities** (`qpos`/`qvel`/`xpos`/`xquat`/`sensordata` → scale, clip, subtract-default, concat, history-stack, quaternion/vector ops). These have no I/O, no unbounded loops, no closures — they are expressible as **declarative data**. The genuine exceptions (terrain raycasting in `HeightScan`, async `.npz` loading in the Mimic terms) are reusable engine-level capabilities, not bespoke per-author logic, and belong in the built-in library rather than in per-simulation code.

**Decision:** mjswan supports **two representations** for MDP terms, and the build records which one each term uses:

1. **Declarative terms** — author-supplied Python functions written in mjlab style (taking a symbolic `env` argument) that are **traced** at build time into a **composition graph** (DAG) of primitive operations against named state slots. The graph is serialized as data into `config.json` / `policy.json`; the engine interprets it with no per-simulation code. This is the default and covers the full range of browser-runnable MDP categories.

   - **Coverage.** Observations, terminations, reset events, domain-randomization events, commands are **func-based and traced** (below). Actions are the one exception: mjlab models actions as a *class-based* closed set (`ActionTermCfg` is an ABC with `build() -> ActionTerm`, no `func` field), not author functions, so mjswan mirrors that — actions stay a fixed built-in set (`JointPosition`, `JointEffort`, `Muscle`) serialized as params. They are still declarative and Cloud-safe (no author code, no `ts_src`), but they are *not* traced from a symbolic-env function and have no per-author escape hatch. Training-only categories (rewards, curriculums, metrics) are out of scope — they have no browser-side runtime equivalent.

   - **Authoring API.** Two entry points, both producing the same traced DAG:
     - *Direct.* A mjswan author passes a traceable function straight to the term cfg: `ObservationTermCfg(func=my_term)`. No binding object, no registration — the build traces it.
     - *mjlab name binding.* To resolve an mjlab function *by name* (the mjlab adapter only sees `func.__name__`), mjswan keeps a binding layer — `MjlabMdpBinding` (the former `ObsFunc`/`TermFunc`/`EventFunc`/`CommandTermSpec`) — that maps an mjlab name to one of three mutually-exclusive modes: a traceable builder (declarative), a `ts_src` path (custom-JS escape hatch), or an `unsupported_reason` marker (accepted for mjlab-config compatibility, fails at build with a clear message). mjswan's own built-in terms (`base_lin_vel`, `joint_pos_rel`, …) are exactly these bindings.

     Authors write functions with the same signature as mjlab (`def my_term(env, **kwargs)`), but `env` is a *symbolic* object. Property accesses (`env.entity("robot").data.root_link_lin_vel_b`) and operator calls (`a - b`, `abs(x)`, `>`) construct primitive-op nodes instead of returning live tensors. The build invokes each function once with this symbolic env and emits the resulting DAG. Control flow over Python values (booleans/ints passed in `params`, including `for name in body_names:` where `body_names` is a static param — this is how list-valued terms like `RobotBodyPosB` unroll) selects branches/iterations at trace time and is fine; control flow over symbolic tensor values is unsupported and surfaces as a build error pointing to the offending line.

   - **Three closed registries.** The engine exposes:
     - **Input slot registry** — readable state. Raw MuJoCo (`qpos`, `qvel`, `xpos`, `xquat`, `sensordata`) plus higher-level mjlab-aligned derived slots (`@entity.<name>.root_link_lin_vel_b`, `@entity.<name>.joint_pos_biased`, `@entity.<name>.default_joint_pos`, …), policy slots (`@policy_output`, `@prev_action`), command slots (`@command.<name>.<field>`), episode slots (`@step_count`), and `@param.<name>`.
     - **Target slot registry** — writable state and model fields used by events. State targets (`qpos[joint]`, `qvel[joint]`, `ctrl[joint]`); DR model targets that the engine supports mutating at runtime (`body_mass[body]`, `body_inertia[body]`, `joint_damping[joint]`, `joint_friction[joint]`, `actuator_gain[actuator]`, `geom_friction[geom]`, …). The exact target list is implementation-defined and grows as the engine adds runtime-mutation support.
     - **Primitive op registry** — the closed set of operators the engine knows how to evaluate (`Add`, `Sub`, `Mul`, `Neg`, `Abs`, `Index`, `Slice`, `Concat`, `Clip`, `UniformRandom`, `QuatApplyInv`, `QuatMul`, `QuatToRot6d`, `History(steps=N)`, `SpawnCapture`, comparison/boolean ops, …). Stateful primitives (`History`, `SpawnCapture`) are nodes; the *graph* stays stateless data but the *interpreter* holds per-node state across steps and clears it on reset.

   - **Per-kind envelope.** Each term kind has its own root structure wrapping a shared primitive graph:
     - obs / termination: a single expression DAG returning a tensor / bool, optionally wrapped by `scale`, `clip`, `history_length` for the existing `ObservationTermCfg` pipeline.
     - event (reset / DR): `{"kind": "event", "mutations": [...]}` where each mutation is a descriptor `{target, op, sample, select?, clip_to_limits?}` — `target` is a writable slot (`joint_qpos`, `joint_qvel`, `freejoint_pos`, `freejoint_yaw`), `op` is `add`/`set`/`compose`, and `sample` is a uniform-distribution descriptor evaluated per target element. Reset events mutate `mjData`. (Events are side-effects, so a structured mutation descriptor — still pure data — is used in place of a value DAG.)
     - command: today's commands are already representation-conformant without a DAG — UI-driven commands (`velocity_command`/`ui_command`) serialize as declarative UI-input data, and motion tracking is an engine-capability named class (`TrackingCommand`, no `ts_src`). Only bespoke commands use the `ts_src` escape hatch. A `sample_expr` DAG (re-evaluated on a `reset`/`step`/`manual` trigger, with optional UI override) is the forward-looking path for commands that today still need `ts_src`; it is not required by current coverage.
     - action: *not* a traced graph (see Coverage). A closed built-in set mirroring mjlab's `ActionTermCfg` subclasses, serialized as `{"type": "JointPosition", ...params}`. Always declarative.

   - **On-wire format.** ONNX-shaped JSON: `{inputs: [...], nodes: [{op, in, out, attrs}], output: ...}`. Named edges (not positional refs) so `policy.json` is human-readable. Not literal ONNX/protobuf — the engine ships a tiny JSON interpreter, not an ONNX runtime.

2. **Custom-JS terms** — the existing `ts_src` escape hatch, retained for the long tail that needs engine-level capabilities mjswan does not yet provide as primitives or derived slots (raycasting, async asset loading, large bespoke state machines). These still compile into a per-build bundle.

The build emits a single aggregate `uses_custom_js` boolean at the top level of `config.json` so a consumer can enforce a **declarative-only** policy with one fetch. Per-term classification is implicit — an entry is custom-JS iff its Python sentinel was registered with `ts_src` — so it does not need to be serialized into each term's JSON entry. If finer-grained reporting is needed later (e.g. telling an author *which* term blocked a Cloud upload), it can be derived from the build's Python context or surfaced through `mjswan info` without changing the on-disk schema. mjswan Cloud accepts only declarative builds; standalone/local use (`mjswan view`/`serve`) accepts both. See the platform-side decision in mjswan-cloud [ADR 0001](https://github.com/ttktjmt/mjswan-cloud/blob/main/docs/adr/0001-self-host-simulations-on-r2.md).

## Considered options

- **Declarative-only (drop `ts_src` entirely).** Rejected: kills the genuine long tail (raycasting, async assets) before those capabilities exist as primitives, and breaks existing custom-term users with no escape hatch.
- **Custom-JS only + sandbox it downstream.** Rejected: keeps arbitrary author code in every build, forcing every consumer to isolate execution (sandboxed iframe / separate origin) and accept residual CPU-abuse risk. Pushes a security burden onto every consumer instead of removing it at the source.
- **Monolithic named-term registry per task.** Rejected: an earlier iteration of this work added one engine TS class per task-specific term (e.g. `BadAnchorPosZOnly`, `OutOfTerrainBounds`, `EeToObjectDistance`). This kept the engine code-free for Cloud but **shifted the engine-extension burden to task authors** — every new task term required an engine PR + release, defeating the "expressible as declarative data" thesis at line 5. The composition-graph approach below subsumes this: task-specific terms become combinations of primitives, no engine PR required.
- **Composition graph of primitive ops, traced from mjlab-style Python (chosen).** Lets mjswan stay maximally expressive for local authoring (mjlab-aligned `func=...` API) while letting untrusted-rendering consumers opt into a provably code-free subset. The composition graph is data; the engine ships a fixed primitive registry that closes the validation contract.

## Consequences

- The build computes the aggregate `uses_custom_js` flag by walking the four func-based `_custom_registry` dicts (observations / terminations / events / commands) and OR-ing whether any registered binding has a non-None `ts_src`. Actions are excluded by construction — they are an always-declarative closed set with no `ts_src` path (see Coverage). A term backed by `ts_src` is custom-JS even though its `policy.json` wrapping resembles a declarative entry.
- **Naming.** The former per-kind sentinels `ObsFunc` / `TermFunc` / `EventFunc` / `CommandTermSpec` are unified/renamed to `MjlabMdpBinding` — their job is binding an mjlab function *name* to a declarative builder, a `ts_src` escape hatch, or an `unsupported_reason`. Authors writing their own terms bypass this entirely via `TermCfg(func=...)` (traced directly).
- A transitional check refused any custom (`ts_src`) binding whose `ts_name` collided with a *named* declarative built-in (the two shared the `{"name": ...}` schema, so the engine's registry spread order would silently pick a winner). Every built-in obs/term/event is now a composition graph and the engine registries (`Observations`/`Terminations`/`Events`) carry only `ts_src` custom classes — no named built-in classes remain — so a `ts_src` term has nothing to shadow. The check had no surface left and was removed.
- Declarative terms are **traced**, not invoked, at serialization time. The mjswan DSL provides a symbolic `env` whose property/method accesses build primitive-op nodes instead of returning live tensors. Authors write functions in mjlab style; the build emits the resulting DAG into the JSON payload. Tracing failures (Python control flow over a symbolic value, indexing by a non-static integer, …) surface as build errors with a pointer to the offending line.
- The shared engine exports three registries — input slots, target slots, primitive ops — so a consumer can validate that a build references only known names. Validation is set-membership only: cheap, decidable, no semantic interpretation required. The registries are versioned alongside the engine bundle; adding entries is backwards-compatible, removing or changing semantics is a breaking change handled by mjswan-cloud's `SUPPORTED_ENGINE_VERSIONS` mechanism (see mjswan-cloud ADR 0001 §3.5).
- All existing monolithic engine built-ins (`JointPos`, `BaseLinearVelocity`, `MotionAnchorPosB`, …) and the 10 task-specific classes added in the first pass of this ADR are **rewritten as composition graphs** under this design. The engine retains a compact set of derived primitive ops (one per mjlab data field, e.g. `RootLinkLinVelB`, `JointPosBiased`) so authors do not have to re-derive base-frame transforms by hand; everything beyond those is composition. Migration is staged: the new composition layer ships first as additive; existing built-ins are rewritten over subsequent PRs; the legacy `{"name": X, ...params}` shape is removed once all built-ins are migrated.
- Expanding the primitive set remains an engine contribution (the same review path as before), but the *expected frequency* of such PRs drops sharply: new entries are added only when a new mjlab data field appears, when a DR mutation target is added, or when `HeightScan`/Mimic-class capabilities migrate in. Task-specific terms no longer require any engine work.
- Genuinely novel logic that cannot be expressed declaratively is not publishable to mjswan Cloud until the missing primitive lands as an engine contribution. This is the intended trade for eliminating foreign code on the platform.
